Ecosistema corporativo CloudTime para el control de asistencia laboral multi-tenant

1. Presentación de la Aplicación Core

CloudTime es una plataforma de software SaaS multi-tenant diseñada para el control y la auditoría de la asistencia laboral. La solución se organiza bajo una arquitectura de Monolito Modular en Spring Boot, lo cual optimiza los costos operativos en infraestructura de nube mientras mantiene un código estructurado y desacoplado listo para escalar.

El valor diferencial del sistema radica en su **circuito de auditoría en tiempo real**. A diferencia de los sistemas de marcación convencionales, CloudTime no delega la confianza en el dispositivo del empleado. En su lugar, el backend valida de forma estricta:

  • La integridad del hardware del dispositivo móvil (detección de emulación de coordenadas GPS o *Mock Locations*).
  • La identidad biométrica del trabajador mediante reconocimiento y emparejamiento facial.
  • La geolocalización física contrastada con geocercas permitidas mediante fórmulas de distancia matemática.

Para asegurar la experiencia de usuario y el rendimiento, los procesos de red lentos e integraciones con la nube (notificaciones, logs de anomalías y alertas masivas) se procesan de forma asíncrona mediante programación concurrente multihilo, aislando el hilo principal de peticiones del servidor Tomcat.

Justificación Técnica del Diseño de Hilos

La llamadas de integración de red externas (notificar a **AWS SNS** o emitir eventos a través de **WebSockets**) introducen latencias aleatorias. Si este procesamiento fuera secuencial en el hilo HTTP Tomcat principal, el usuario móvil percibiría lentitud o podría sufrir timeouts de red.

Al implementar `@Async` de Spring Boot, se realiza un **Fork**: el hilo síncrono del cliente responde de inmediato arrojando el error `BadRequestException`, liberando la conexión de red del dispositivo en milisegundos. Paralelamente, el hilo asíncrono secundario escribe la auditoría en la base de datos de Supabase, conecta con AWS SNS y despacha el aviso en tiempo real a los administradores.

Estructura Modular

La arquitectura del monolito divide el sistema en cuatro capas lógicas:

  • Capa de Seguridad: Intercepta, desencripta y valida el token JWT de entrada.
  • Capa de Identidad: Contiene las entidades maestras que configuran el tenant (`Empresa`, `Empleado`, `ReglasHorario`).
  • Capa de Operación: Captura y evalúa la telemetría del día a día (fichajes, anomalías y auditoría).
  • Capa de Cierre: Ejecuta cálculos periódicos de nóminas, solicitudes de vacaciones y maneja archivos adjuntos (`Media` con Amazon S3).

Estrategia de Redes y Seguridad

  • Aislamiento Perimetral (VPC): Los contenedores backend y la base de datos están en subredes privadas. Ningún recurso puede ser contactado directamente desde internet; toda llamada HTTP externa debe cruzar el **Application Load Balancer (ALB)** en la subred pública.
  • Tolerancia a fallos física (Multi-AZ): El cluster de **ECS Fargate** distribuye las tareas en dos Availability Zones físicas independientes de AWS (`us-east-1a` y `us-east-1b`). Si una zona sufre un apagón, el ALB desvía el 100% de la carga a la otra zona de inmediato de forma transparente.
  • RDS Multi-AZ: PostgreSQL mantiene una réplica en espejo síncrona en otra AZ física, garantizando failover automático y recuperación de conexión JDBC en < 60 segundos.

7. Registro de Decisiones Arquitectónicas (ADR)

Consolidado de las decisiones clave de arquitectura tomadas para estructurar CloudTime:

ADR 1: Autenticación Stateless con JWT Aceptada
Contexto y Requisito
La alta concurrencia de marcaciones de asistencia en horas pico puede saturar servidores que manejan sesiones en memoria o base de datos. Se requiere un mecanismo stateless y multi-tenant seguro para autorizar peticiones de la API de forma rápida.
Decisión Adoptada
Implementar tokens **JWT firmados asimétricamente (RSA-256)** que transportan claims de identidad, rol, modalidad del empleado y críticamente, el `empresaId` del tenant para aislar automáticamente todas las consultas SQL en Hibernate.
Consecuencias
Ventajas (Pros)
Escalabilidad horizontal ilimitada (stateless), y validaciones matemáticas en memoria de JVM sin viajes de red redundantes.
Desventajas (Cons)
Dificultad para invalidación de sesión inmediata desde el servidor (mitigado con tiempos de vida de 15 minutos y Refresh Tokens).
Alternativas Consideradas
Sesiones tradicionales en PostgreSQL (descartado por sobrecarga de red y base de datos) o Spring Session Redis (postergado para reducir costos de infraestructura iniciales en AWS).
ADR 2: Selección del Tipo de Base de Datos (PostgreSQL) Aceptada
Contexto y Requisito
Los registros de asistencia, contratos y pre-nóminas representan datos de carácter legal y financiero. Se requiere integridad referencial fuerte, transacciones ACID consistentes y soporte para consultas matemáticas de distancia (fórmula Haversine).
Decisión Adoptada
Utilizar la base de datos relacional **PostgreSQL 15 (AWS RDS Multi-AZ / Supabase)** acoplada a Hibernate ORM para encapsular las políticas de multi-tenancy lógico mediante el discriminador `@TenantId`.
Consecuencias
Ventajas (Pros)
Garantías transaccionales ACID fuertes para el motor de nóminas, llaves foráneas a nivel de motor y consultas complejas simplificadas.
Desventajas (Cons)
Dificultad de escalado horizontal de escritura (mitigado con HikariCP y replicación con réplicas de lectura RDS).
Alternativas Consideradas
Bases de datos NoSQL como MongoDB o DynamoDB (descartadas por carecer de integridad referencial nativa e ineficiencia en uniones/JOINs financieros).
ADR 3: Estilo de Integración entre Componentes Aceptada
Contexto y Requisito
Se requiere un canal estándar para comunicación síncrona cliente-servidor, pero al mismo tiempo se necesita despachar efectos secundarios pesados (como alertas push) sin bloquear al usuario en su app móvil.
Decisión Adoptada
Implementar **APIs RESTful** síncronas usando HTTP/JSON para interacciones directas, y un broker de **mensajería asíncrona (AWS SNS)** para publicar incidentes de seguridad y notificaciones de forma desacoplada.
Consecuencias
Ventajas (Pros)
Desacoplamiento total de alertas de auditoría, compatibilidad móvil/web universal y liberación inmediata del hilo HTTP principal.
Desventajas (Cons)
Consistencia eventual en las notificaciones al administrador y complejidad adicional de tracing de llamadas distribuidas.
Alternativas Consideradas
GraphQL (descartado por complejidad multi-tenant en esta fase) o gRPC (descartado por falta de soporte nativo simple desde navegadores web).
ADR 4: Estrategia de Comunicación en Tiempo Real Aceptada
Contexto y Requisito
El departamento de seguridad requiere enterarse inmediatamente de anomalías graves de fraude en marcación de asistencia sin saturar la red con consultas repetitivas de refresco de datos.
Decisión Adoptada
Habilitar comunicación bidireccional mediante **WebSockets y el protocolo STOMP** en Spring Boot. El backend publica los eventos directamente en el topic `/topic/anomalias` y los navegadores suscritos los reciben en milisegundos.
Consecuencias
Ventajas (Pros)
Latencia casi nula de alertas en vivo, eliminación completa de tráfico de polling y menor sobrecarga de base de datos PostgreSQL.
Desventajas (Cons)
Mayor uso de sockets TCP activos y memoria en el servidor (mitigado mediante dimensionamiento de contenedores de ECS).
Alternativas Consideradas
HTTP Short Polling (descartado por ineficiencia de red y sobrecarga de queries de base de datos) o Server-Sent Events (SSE).
ADR 5: Organización del Código (Monolito Modular) Aceptada
Contexto y Requisito
Se requiere velocidad de desarrollo y despliegues ágiles manteniendo una infraestructura de nube económica, pero impidiendo que el código de la aplicación se vuelva caótico y acoplado.
Decisión Adoptada
Adoptar una arquitectura de **Monolito Modular** organizando el backend en un único repositorio con cuatro capas desacopladas con dependencias estrictas unidireccionales, empaquetadas en un único Docker ejecutable para ECS Fargate.
Consecuencias
Ventajas (Pros)
Costos operativos de nube muy bajos, compilación y despliegue simple (CI/CD rápido), transaccionalidad relacional nativa y refactorización a microservicios futura sencilla.
Desventajas (Cons)
Punto único de falla físico (un fallo de memoria JVM afecta la disponibilidad de todo el backend).
Alternativas Consideradas
Microservicios independientes (descartados por alta complejidad operativa de red, latencia inter-servicio y necesidad de balanceadores y VPC PrivateLinks múltiples).

Análisis ATAM (Escenario ESC-02: 200 marcaciones/segundo concurrentes)

1. Enfoque Arquitectónico

Utilización de **escalamiento horizontal stateless** a través de un Application Load Balancer y ECS Fargate. La CPU e I/O de red del servidor se protegen derivando el procesamiento y las llamadas de red externas (AWS SNS y WebSockets) a hilos asíncronos `@Async` separados.

2. Puntos Sensibles

La dimensión del pool de conexiones **HikariCP** de Spring (un pool muy pequeño bloquea los hilos de Tomcat y uno muy grande satura RDS PostgreSQL), el dimensionamiento de CPU/RAM asignado a las ECS Tasks para descifrar firmas JWT, y el tamaño de la cola de hilos de tareas `@Async`.

3. Trade-offs (Compromisos)

Se sacrifica la **Eficiencia de Costos de AWS** al mantener infraestructura redundante y escalable Multi-AZ. También se compromete la **Consistencia Inmediata** de auditoría (el administrador web ve las alertas por fraude con consistencia eventual / retraso de 1 a 3 segundos) para proteger la velocidad de marcación.

4. Riesgos & No-Riesgos

Riesgos (R): Goteras de conexión JDBC si un reporte mensual corre durante la hora pico en el RDS transaccional principal (`R-01`), y latencia añadida si la clave pública JWT se consulta síncronamente desde una API externa en cada request (`R-02`).

No-Riesgos (NR): Validación de firmas JWT en la memoria de la JVM con claves precargadas (`NR-01`), y aislamiento completo de fallos del SDK de AWS SNS mediante el procesamiento asíncrono `@Async` (`NR-02`).

 AdminRrhhController.generarPrenomina(...) recibe el payload JSON e invoca a PrenominaServiceImpl. El Hilo Principal (Tomcat HTTP Thread) recibe la llamada de forma síncrona y realiza la validación de permisos del token JWT. El Cliente (Panel Web) envía la petición HTTPS cruzando el **Internet Gateway** de AWS. El **ALB** distribuye el tráfico hacia una de las **ECS Tasks** (Task A/B).
2. Desacoplamiento (Fork)
El sistema crea la tarea asíncrona en segundo plano para evitar fallos de timeout. 		• ReportePrenominaMensual (Instanciada con estado PROCESANDO) PrenominaServiceImpl crea el registro inicial en base de datos y retorna la respuesta ID de inmediato al controlador. Bifurcación de hilos (Fork):
  • • Hilo HTTP retorna 202 Accepted.
  • • Hilo asíncrono @Async inicia el procesamiento batch.
 La **ECS Task** finaliza la petición HTTP y libera el canal de red. **RDS PostgreSQL** persiste el cambio de estado del reporte a PROCESANDO.
3. Extracción de Datos
El motor asíncrono lee registros de asistencia y contratos del mes.
  • • Empleado (Lista de activos)
  • • RegistroAsistencia (Marcaciones)
 PrenominaServiceImpl consulta los repositorios EmpleadoRepository y RegistroAsistenciaRepository de JPA. El **Hilo @Async** realiza la lectura paginada de los datos históricos de asistencia para proteger la memoria RAM del contenedor Fargate. La tarea de **ECS Fargate** ejecuta las consultas SQL pesadas mediante conexiones JDBC directas sobre la base de datos **RDS PostgreSQL Primary**.
4. Cálculo Salarial
El servicio calcula horas trabajadas, extras, recargos y ausencias.
  • • ContratosEmpleados
  • • CalculadoraPrenominaService
 CalculadoraPrenominaService.calcular(...) aplica las fórmulas matemáticas y reglas salariales por cada empleado. El **Hilo @Async** ejecuta la computación matemática en memoria RAM y CPU aislada. Uso intensivo de recursos de CPU y memoria JVM dedicados dentro de la instancia de contenedor virtual de **ECS Task**.
5. Guardado de Reporte
Consolidación del archivo CSV inmutable y actualización en base de datos. 		• ReportePrenominaMensual (Se completa la URL de S3, totales y montos) DocumentoExportService escribe el archivo físico y sube a AWS S3. Guarda la entidad actualizada mediante ReporteRepository.save(...). El **Hilo @Async** escribe en el almacenamiento efímero temporal y luego transmite el archivo mediante I/O de red hacia S3. La **ECS Task** sube el CSV físico al bucket de **Amazon S3** (cloudtime-media-storage-dev) y actualiza el estado a COMPLETO en **RDS PostgreSQL**.
6. Notificación Final
Alerta por correo, push y actualización en tiempo real en los paneles.
  • • AlertaService
  • • AnomaliasGravesAuditoria
 AlertaService.publicarEventoFinalizacion(...) publica en AWS SNS y gatilla notificaciones WebSockets. El **Hilo @Async** envía tramas WebSocket y notifica al broker de mensajería antes de realizar el **Join** y finalizar su ciclo de vida. La **ECS Task** publica un evento mediante SDK en **Amazon SNS** (cloudtime-business-events-dev) para alertas por SMS o e-mail.

🗣️ Guía de Explicación Multidimensional (Sustentación de Flujo)

1. Vista de Clases: Dominio de Datos

El motor de cálculo opera sobre entidades de negocio bien estructuradas. Utiliza la relación multi-tenant de Empresa para aislar y recuperar la lista de Empleado. Examina recursivamente cada RegistroAsistencia y lo contrasta con el salario y jornada definidos en ContratosEmpleados, consolidando la información final en un registro inmutable de ReportePrenominaMensual.

2. Vista de Secuencia: Comportamiento API

La interacción se ejecuta de manera estructurada y limpia. La API REST expone el endpoint en AdminRrhhController, el cual delega la orquestación a PrenominaServiceImpl. Este servicio coordina los accesos a datos mediante Repositorios JPA y delega la ejecución de la matemática salarial al procesador puro de negocio: CalculadoraPrenominaService.

3. Vista de Actividad: Concurrencia y Rendimiento

Para mitigar los temidos fallos de timeout de red (donde peticiones largas de más de 30s son interrumpidas con un error **HTTP 504 Gateway Timeout** por el ALB de AWS), el backend realiza una bifurcación de hilos (Fork/Join). El controlador HTTP Tomcat delega de inmediato el cálculo a un hilo secundario asíncrono gestionado mediante @Async de Spring Boot, liberando el hilo web y retornando de inmediato un HTTP 202 Accepted para asegurar una interfaz fluida.

4. Vista de Despliegue: Infraestructura AWS

A nivel de infraestructura física, el tráfico HTTPS es ruteado por el **Application Load Balancer (ALB)** a las tareas stateless de **ECS Fargate** en subredes privadas. La base de datos es una instancia **RDS PostgreSQL Multi-AZ**. Los archivos masivos CSV resultantes se suben a **Amazon S3** para descarga a largo plazo, y el aviso final de generación exitosa se distribuye asíncronamente mediante **Amazon SNS**.

💡 Patrón Arquitectónico de Asincronía para Procesamiento Batch
Este diseño multi-vista demuestra cómo la asincronía a nivel de código (Vista de Actividad) se comunica directamente con la persistencia inmutable en AWS S3 y RDS (Vista de Despliegue), protegiendo la disponibilidad de hilos de Tomcat y eliminando la posibilidad de caídas de conexión por latencia en el ALB de AWS.
